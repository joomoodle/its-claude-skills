# Skill: migrate-sqlserver-pg
Trigger: `/migrate-sqlserver-pg`

Migración completa de una Web API .NET (EF Core) de SQL Server a PostgreSQL en Cloud SQL (GCP).
Cubre: cambios de código, esquema Flyway, script Python de datos, CI/CD y runbook operacional.

---

## REGLAS ABSOLUTAS — nunca violar

1. **No cambiar nombres de proyectos, namespaces, soluciones ni carpetas.**
2. **No usar `AppContext.SetSwitch` para Npgsql** (deprecated desde Npgsql 9).
3. **No hardcodear credenciales en ningún archivo.** Siempre usar variables de entorno.
4. **No usar `RETURNS SETOF RECORD` en funciones PG** — usar `RETURNS TABLE(...)`.
5. **No concatenar input del usuario en queries** — CA2100/CA3001. Siempre parámetros.
6. **No agregar `GRANT <rol> TO <usuario>`** en migraciones Flyway. Es paso manual del DBA con superusuario.
7. **NO cambiar `DateTime.Now` a `DateTime.UtcNow`** en el código de negocio.

## Fase 1 — Cambios EF Core (.NET)

### 1.1 NuGet packages

En el `.csproj` del proyecto `ServiceImplementation`:
- **Quitar**: `Microsoft.Data.SqlClient`, `Microsoft.EntityFrameworkCore.SqlServer`
- **Agregar**: `Npgsql.EntityFrameworkCore.PostgreSQL`, `EFCore.NamingConventions`

### 1.2 DbContext — DI registration

```csharp
// En Program.cs / Startup.cs
builder.Services.AddDbContext<SuiteDbContext>(options =>
    options.UseNpgsql(builder.Configuration.GetConnectionString("DBSuite"))
           .UseSnakeCaseNamingConvention());
```

No usar `AppContext.SetSwitch("Npgsql.EnableLegacyTimestampBehavior", true)`.

### 1.3 ConfigureConventions — mapeo global de DateTime

```csharp
protected override void ConfigureConventions(ModelConfigurationBuilder configurationBuilder)
{
    configurationBuilder.Properties<DateTime>()
        .HaveColumnType("timestamp without time zone");
    configurationBuilder.Properties<DateTime?>()
        .HaveColumnType("timestamp without time zone");
}
```

Esto evita el error `Cannot write DateTime with Kind=Local to PostgreSQL type 'timestamp with time zone'`.

### 1.4 IEntityTypeConfiguration<T>

Toda la configuración va en clases `Configuration/`. No usar anotaciones en entidades.
`UseSnakeCaseNamingConvention()` ya mapea nombres automáticamente; solo agregar overrides explícitos donde el algoritmo falla (ej. columnas todo-minúsculas como `fechafin`).

### 1.5 Owned types

Si alguna entidad usa `OwnsOne(...)`, EF Core Npgsql la mapea a `jsonb` en lugar de columnas planas.
Estas tablas **no se pueden migrar con el script Python** — requieren construcción manual del JSON.
Agregar el nombre SQL Server a `SKIP_SQL_TABLES` en el script.

## Fase 2 — Roles y esquema Flyway

### 2.1 Estructura de directorios

```
db/
  flyway.conf
  roles/
    00_roles_y_permisos.sql
  migrations/
    V001__baseline_schema.sql
    V002__...sql               # (opcional, reservar para proc. almacenados si aplica)
    V003__grant_permissions.sql
```

### 2.2 flyway.conf

```properties
flyway.locations=filesystem:db/migrations
flyway.schemas=public
flyway.defaultSchema=public
flyway.baselineOnMigrate=false
flyway.validateMigrationNaming=true
flyway.initSql=SET ROLE db_creator;
```

`initSql=SET ROLE db_creator` hace que Flyway ejecute cada migración como ese rol, garantizando que las tablas queden owned por `db_creator`.

### 2.3 Roles — 00_roles_y_permisos.sql (idempotente)

```sql
DO $$ BEGIN
  IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'db_creator') THEN
    CREATE ROLE db_creator NOLOGIN;
  END IF;
  IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'usr_app_role') THEN
    CREATE ROLE usr_app_role NOLOGIN;
  END IF;
  IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'dev_team') THEN
    CREATE ROLE dev_team NOLOGIN;
  END IF;
  IF NOT EXISTS (SELECT FROM pg_roles WHERE rolname = 'usr_dba_role') THEN
    CREATE ROLE usr_dba_role NOLOGIN;
  END IF;
END $$;

-- Permisos sobre schema public
GRANT USAGE ON SCHEMA public TO usr_app_role, dev_team, usr_dba_role;

-- Auto-grants para tablas futuras creadas por db_creator
ALTER DEFAULT PRIVILEGES FOR ROLE db_creator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO usr_app_role;
ALTER DEFAULT PRIVILEGES FOR ROLE db_creator IN SCHEMA PUBLIC
  GRANT SELECT ON TABLES TO dev_team, usr_dba_role;

-- NOTA: GRANT usr_app_role TO <usuario> es paso MANUAL del DBA. NO va aquí.
```

### 2.4 V001 — convenciones de esquema

- Columnas identity: `generated by default as identity`
- Timestamps: `timestamp without time zone` (nunca `timestamptz`)
- Nombres: snake_case (generado por `UseSnakeCaseNamingConvention`)
- FKs explícitas con `CONSTRAINT fk_... FOREIGN KEY (...) REFERENCES ...`
- Al final del V001:

```sql
-- Permisos sobre tablas ya creadas
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO usr_app_role;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO dev_team, usr_dba_role;

ALTER DEFAULT PRIVILEGES FOR ROLE db_creator IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO usr_app_role;
ALTER DEFAULT PRIVILEGES FOR ROLE db_creator IN SCHEMA public
  GRANT SELECT ON TABLES TO dev_team, usr_dba_role;
```

### 2.5 V003 — grant explícito para ambientes con V001 como baseline

Para ambientes donde V001 ya existía y se marcó como baseline, los `ALTER DEFAULT PRIVILEGES` de V001 no otorgaron permisos en tablas existentes. Crear `V003__grant_permissions.sql` con `GRANT ... ON ALL TABLES`:

```sql
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO usr_app_role;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO dev_team, usr_dba_role;
```

### 3.3 Algoritmo snake_case — to_snake()

El algoritmo de Humanizer necesita una corrección para el prefijo `id`:

```python
import re

def to_snake(name: str) -> str:
    # PRIMERO: idusuarioAct → id_usuarioAct (prefijo id + minúscula)
    s = re.sub(r"^id([a-z])", r"id_\1", name)
    # Luego: separaciones estándar camelCase/PascalCase
    s = re.sub(r"([A-Z]+)([A-Z][a-z])", r"\1_\2", s)
    s = re.sub(r"([a-z\d])([A-Z])", r"\1_\2", s)
    s = re.sub(r"[-\s]", "_", s)
    return s.lower()
```

Sin el primer `re.sub`, `idusuarioAct` → `idusuario_act` (incorrecto), cuando PG espera `id_usuario_act`.

### 3.6 Columnas de auditoría — relajar NOT NULL antes de migrar

Filas históricas en SQL Server pueden tener NULL en columnas de auditoría incluso si el esquema PG las define NOT NULL.

```python
AUDIT_COLS = {"id_usuario_act", "fecha_act", "ip_act", "mac_address_act", "fecha_fin"}

def _relax_audit_not_null(pg_conn) -> None:
    cur = pg_conn.cursor()
    cur.execute("""
        SELECT table_name, column_name
        FROM information_schema.columns
        WHERE table_schema = 'public'
          AND is_nullable = 'NO'
          AND column_name = ANY(%s)
    """, (list(AUDIT_COLS),))
    for table, col in cur.fetchall():
        cur.execute(f'ALTER TABLE "{table}" ALTER COLUMN "{col}" DROP NOT NULL')
    cur.close()
    pg_conn.commit()
```

Llamar esto **antes** de comenzar la migración de datos.

### 3.7 Coerción de tipos bool → int

pymssql devuelve `bit` de SQL Server como `bool` de Python. Si la columna PG es `integer/smallint/bigint` (ej. `id_estatus` en algunas tablas), hay que castear. Si la columna PG es `boolean`, NO castear.

```python
def pg_column_types(cur, table: str) -> dict[str, str]:
    cur.execute("""
        SELECT column_name, data_type
        FROM information_schema.columns
        WHERE table_schema = 'public' AND table_name = %s
    """, (table,))
    return {r[0]: r[1] for r in cur.fetchall()}

# Al migrar cada tabla:
col_types = pg_column_types(pg_cur, pg_table)
int_cols = {col for col, dtype in col_types.items() if dtype in ("integer", "smallint", "bigint")}

def _coerce(v, pg_col: str = ""):
    if isinstance(v, uuid.UUID):
        return str(v)
    if isinstance(v, bool) and pg_col in int_cols:
        return int(v)
    return v
```

### 3.8 psycopg2 y PL/pgSQL — `%I` vs `%%I`

psycopg2 solo procesa `%s`/`%I` cuando se pasa el segundo argumento `params`.
Sin `params`, envía el SQL verbatim — por eso usar `%I` directo (no `%%I`) dentro de bloques `DO $$`:

```python
pg_cur.execute("""
    DO $body$
    DECLARE r record;
    BEGIN
        FOR r IN SELECT tablename FROM pg_tables
                 WHERE schemaname = 'public' AND tableowner != 'db_creator'
        LOOP
            EXECUTE format('ALTER TABLE public.%I OWNER TO db_creator', r.tablename);
        END LOOP;
    END $body$;
""")
# Sin segundo argumento → psycopg2 no toca el string → %I llega a PG correcto
```

### 3.9 Flags del script

| Flag | Descripción |
|------|-------------|
| `--list-tables` | Lista tablas SQL Server sin conectar a ninguna BD |
| `--dry-run` | Conecta, verifica columnas, pero no inserta datos |
| `--verify` | Post-migración: compara conteo SQL Server vs PG |
| `--create-schema` | Aplica roles y V001 si PG no tiene tablas |
| `--fresh` | TRUNCATE RESTART IDENTITY CASCADE en PG antes de migrar |

### 3.10 Orden de ejecución típico (primera vez)

```bash
# 1. Levantar Cloud SQL Auth Proxy (dos instancias si necesario)
./cloud-sql-proxy --address 127.0.0.1 --port 1435 <proyecto>:<region>:<instancia-mssql> &
./cloud-sql-proxy --address 127.0.0.1 --port 5432 <proyecto>:<region>:<instancia-pg> &

# 2. Exportar credenciales
source db/scripts/setup_env.sh

# 3. Activar venv
source db/scripts/.venv/bin/activate

# 4. Dry-run primero para validar mapeo
python db/scripts/migrate_data.py --dry-run --create-schema

# 5. Migración real
python db/scripts/migrate_data.py --create-schema

# 6. Verificar conteos
python db/scripts/migrate_data.py --verify

# 7. Si hay que re-migrar desde cero
python db/scripts/migrate_data.py --fresh
python db/scripts/migrate_data.py --verify
```

## Fase 4 — CI/CD GitLab

### 4.1 validate-migrations (stage: test, con postgres efímero)

```yaml
validate-migrations:
  stage: test
  image:
    name: flyway/flyway:11
    entrypoint: [""]
  services:
    - name: postgres:15
      alias: postgres
      variables:
        POSTGRES_DB: NombreDB
        POSTGRES_USER: postgres
        POSTGRES_PASSWORD: postgres
  variables:
    FLYWAY_CONFIG_FILES: db/flyway.conf
    FLYWAY_URL: "jdbc:postgresql://postgres:5432/NombreDB"
    FLYWAY_USER: postgres
    FLYWAY_PASSWORD: "postgres"
  only:
    changes:
      - db/migrations/**/*
      - db/flyway.conf
      - db/roles/**/*
  before_script:
    - apt-get update -qq && apt-get install -y -qq postgresql-client
    - PGPASSWORD="$FLYWAY_PASSWORD" psql -h postgres -U "$FLYWAY_USER" -d "$POSTGRES_DB"
        -v ON_ERROR_STOP=1 -f db/roles/00_roles_y_permisos.sql
  script:
    - flyway -connectRetries=15 migrate
    - flyway validate
    - flyway info
```

### 4.2 Plantilla Flyway + Cloud SQL Auth Proxy (stage: migrate)

```yaml
.flyway-cloudsql:
  stage: migrate
  image:
    name: flyway/flyway:11
    entrypoint: [""]
  variables:
    PROXY_VERSION: v2.14.1
    PROXY_URL: https://storage.googleapis.com/cloud-sql-connectors/cloud-sql-proxy/${PROXY_VERSION}/cloud-sql-proxy.linux.amd64
    FLYWAY_CONFIG_FILES: db/flyway.conf
    FLYWAY_URL: "jdbc:postgresql://127.0.0.1:1435/NombreDB?sslmode=disable"
  before_script:
    - echo "$SA_KEY" > /tmp/sa.json
    - curl -sSLo /tmp/cloud-sql-proxy "$PROXY_URL"
    - chmod +x /tmp/cloud-sql-proxy
    - /tmp/cloud-sql-proxy --credentials-file /tmp/sa.json --port 1435 "$CLOUDSQL_INSTANCE" &
  script:
    - flyway -user="$DB_USER" -password="$DB_PASSWORD" -connectRetries=20 info
    - flyway -user="$DB_USER" -password="$DB_PASSWORD" repair
    - flyway -user="$DB_USER" -password="$DB_PASSWORD" -connectRetries=20 migrate
```

Nota: el proxy usa puerto `1435` para Cloud SQL PostgreSQL en CI (evita conflictos con postgres local). La `FLYWAY_URL` lleva ese puerto.

### 4.3 baseline-*-db (solo primera vez por ambiente)

```yaml
.flyway-baseline:
  extends: .flyway-cloudsql
  allow_failure: true
  script:
    - flyway -user="$DB_USER" -password="$DB_PASSWORD" -connectRetries=20
        -baselineVersion=1 -baselineDescription="baseline esquema existente" baseline
```

Ejecutar `baseline-dev-db` / `baseline-pre-db` / `baseline-prod-db` manualmente una sola vez cuando el esquema ya existe y se quiere registrar V001 sin ejecutarlo.

### 4.4 Variables de CI necesarias

Para cada ambiente (dev/pre/prod):
- `SA_KEY` — service account JSON (GCP)
- `CLOUDSQL_INSTANCE` — `proyecto:region:instancia`
- `DB_USER` / `DB_PASSWORD` — usuario de migración con CONNECT + permiso de ejecutar DDL como `db_creator`
